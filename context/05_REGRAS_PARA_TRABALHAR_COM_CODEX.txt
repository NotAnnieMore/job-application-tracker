JOB APPLICATION TRACKER
REGRAS PARA TRABALHAR COM O CODEX PASSO A PASSO

1. OBJETIVO

Usar o Codex para acelerar o desenvolvimento sem transformar o projeto numa caixa negra.

O resultado deve ser:
- funcional;
- compreensível;
- testável;
- documentado;
- explicável numa entrevista.

2. REGRA PRINCIPAL

Não pedir:
"Cria a aplicação completa."

Pedir tarefas pequenas:
- criar uma tabela;
- criar um formulário;
- implementar uma validação;
- corrigir um erro;
- adicionar um filtro;
- escrever um teste;
- explicar uma decisão.

3. FORMATO RECOMENDADO PARA CADA TAREFA

Contexto:
Explicar o estado atual do projeto.

Objetivo:
Definir uma única alteração principal.

Ficheiros:
Indicar os ficheiros que podem ser alterados.

Restrições:
Explicar o que não deve ser alterado.

Critérios de aceitação:
Definir como saber se a tarefa ficou concluída.

Explicação:
Pedir um resumo das alterações e das decisões.

Exemplo:

Contexto:
Temos uma aplicação Next.js ligada ao Supabase e a autenticação já funciona.

Objetivo:
Criar a tabela companies e a página para listar empresas do utilizador autenticado.

Restrições:
- Não criar ainda edição ou eliminação.
- Não alterar o layout global.
- Usar português de Portugal.
- Aplicar Row Level Security.

Critérios de aceitação:
- Cada utilizador vê apenas as suas empresas.
- A página mostra estado vazio.
- Os erros são tratados.
- O código compila.

No final:
Explica os ficheiros alterados, as queries utilizadas e a política de segurança criada.

4. FLUXO DE TRABALHO

Para cada funcionalidade:

1. Discutir o comportamento.
2. Confirmar o design.
3. Definir os dados necessários.
4. Criar uma tarefa pequena para o Codex.
5. Rever o plano proposto.
6. Aplicar as alterações.
7. Ler os ficheiros alterados.
8. Executar a aplicação.
9. Testar manualmente.
10. Corrigir erros.
11. Pedir uma explicação.
12. Criar commit.
13. Atualizar documentação.

5. PERGUNTAS QUE DEVEM SER FEITAS ANTES DE ALTERAÇÕES VISUAIS

- Onde aparece esta funcionalidade?
- Deve abrir numa página, modal ou painel?
- Que campos aparecem?
- Quais são obrigatórios?
- Qual é a ação principal?
- Existe ação secundária?
- Como aparece o estado vazio?
- Como aparece o loading?
- Como aparece o erro?
- Como funciona no telemóvel?
- Existe confirmação antes de eliminar?

6. PERGUNTAS QUE DEVEM SER FEITAS ANTES DE ALTERAÇÕES DE DADOS

- Que entidade estamos a criar?
- A quem pertence?
- Que relações tem?
- Quais campos são obrigatórios?
- Quais campos devem ser únicos?
- O que acontece ao eliminar?
- Precisamos de histórico?
- Precisamos de índice?
- Como se aplica Row Level Security?
- Como testamos com dois utilizadores?

7. REGRAS DE QUALIDADE

O Codex deve:
- manter TypeScript estrito;
- evitar any sem justificação;
- validar dados;
- tratar erros;
- usar nomes consistentes;
- evitar duplicação;
- respeitar a estrutura do projeto;
- atualizar tipos;
- não expor segredos;
- não colocar chaves privadas no frontend;
- manter o idioma da interface em português;
- escrever testes quando forem úteis;
- explicar alterações relevantes.

8. REGRAS DE SEGURANÇA

Nunca aceitar sem revisão:
- políticas de Row Level Security;
- alterações de autenticação;
- eliminação em cascata;
- permissões;
- variáveis de ambiente;
- queries que ignorem o utilizador;
- código que exponha tokens;
- operações destrutivas.

9. COMMITS RECOMENDADOS

Exemplos:
- chore: configurar projeto Next.js
- feat: adicionar autenticação com Supabase
- feat: criar gestão de empresas
- feat: adicionar candidaturas
- feat: implementar entrevistas
- feat: adicionar filtros de candidaturas
- fix: corrigir isolamento de dados por utilizador
- docs: documentar modelo de dados
- test: adicionar testes de autenticação

10. DOCUMENTAÇÃO DE DECISÕES

Sempre que existir uma escolha importante, criar uma nota em:
docs/decisions/

Exemplos:
- escolha de Next.js;
- escolha de Supabase;
- estrutura do modelo de dados;
- opção por estados fixos;
- tipo de navegação;
- estratégia de formulários;
- estratégia de testes.

Cada decisão deve registar:
- contexto;
- opções consideradas;
- decisão;
- razões;
- consequências;
- possibilidade de revisão.

11. RECOMENDAÇÕES DURANTE O PROJETO

É normal surgirem recomendações.

Classificação sugerida:
- Obrigatória: segurança, erro crítico ou bloqueio.
- Recomendada: melhora manutenção ou experiência.
- Opcional: melhoria futura.
- Fora do MVP: aumenta demasiado o âmbito.

Antes de aplicar:
- explicar a recomendação;
- indicar impacto;
- indicar custo;
- indicar riscos;
- pedir decisão quando alterar o produto.

12. IDIOMA

A interface começa em português de Portugal.

Regras:
- textos da interface em português;
- nomes internos do código podem ficar em inglês;
- nomes das tabelas e colunas preferencialmente em inglês;
- mensagens visíveis ao utilizador em português;
- documentação técnica pode ser em português;
- preparar o código para futura internacionalização sem a implementar já.

13. DEFINIÇÃO DE CONCLUÍDO

Uma tarefa só está concluída quando:
- código compila;
- funcionalidade funciona;
- erros são tratados;
- interface está coerente;
- segurança foi revista;
- testes relevantes passaram;
- alteração foi explicada;
- documentação foi atualizada;
- commit foi criado.
